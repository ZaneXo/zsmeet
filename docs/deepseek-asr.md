# 接入 DeepSeek 在线识别

在公开的会议录音上，DeepSeek 在线识别比本机 SenseVoice 字错误率低 4～5 个点（AISHELL-4 20.6% → 15.7%，见 [asr-eval.md](asr-eval.md)）。本文记录线上可选接入的设计与实现。

## 前提

- **录音会发给 DeepSeek。** 现在 README 写的是「录音留在服务器上，只有文字发给大模型」。所以在线识别**默认关着**，管理员在设置里看到明确的说明后才能打开；README 里所有说录音不外发的地方都要改成「打开在线识别时除外」。
- **接口的限制**（[文档](https://api-docs.deepseek.com/zh-cn/guides/asr)）：一次最多 120 秒、8 MiB；只返回文字，**没有每个字或每句的时间**；没有热词参数；每个账号最多同时 50 个请求；按录音时长计费，刊例价每小时 0.78 元。
- 转写要按句存、每句带时间：搜索跳转、播放高亮、区分说话人（按时间把说话人对到句子上）都靠它。所以**本地的 SenseVoice 照样要跑**，用它的每个字的时间给 DeepSeek 的文字定时间。SenseVoice 在 CPU 上只要录音时长的 0.025 倍，多跑这一遍不贵；在线识别失败时也直接用它的结果。

## 流程

```
转码（含音量处理）
  → VAD + SenseVoice：带时间的字（现在就有）
  → 在线识别：按 VAD 的停顿切成最长 100 秒的段，同时发给 DeepSeek      ┐ 两步同时做：
  → 区分说话人（3D-Speaker 的做法，internal/diarize）                ┘ 一个等网络，一个吃 CPU
  → 对齐：把 DeepSeek 每段的文字和同一段里 SenseVoice 的字逐字对上，借时间，再按标点切句
  → 按时间分配说话人 → 按热词读音纠错 → 大模型校对 → 写纪要（和现在一样）
```

### 切段

- 用 SenseVoice 那一步的 VAD 结果（有人说话的区间）。从一个区间的开头起，把后面的区间连同中间的停顿合进来，到 100 秒为止；段和段之间的停顿不发。测评里就是这么切的（25.1～25.8% 就是这种切法的结果），整段送比一句一个请求低 2～4 个点。
- 只在停顿处切，不会把一个字切成两半。VAD 已经保证每个区间最长 10 秒，所以一定切得出不超过 100 秒的段。
- 编成 16 位 16k 单声道 WAV，100 秒约 3.2 MB，在 8 MiB 以内。

### 对齐（新写，最要紧的一步）

DeepSeek 返回一段文字，SenseVoice 在同一段里给出一串带时间的字。两边去掉标点、数字统一成汉字读法（评测里已经有 `spokenNumbers`）后，按字做编辑距离对齐：

- 对上的字和被替换的字：用 SenseVoice 那个字的时间。
- DeepSeek 多出来的字（SenseVoice 漏掉的话，这正是在线识别好的地方）：在前后两个有时间的字之间按字数均匀摊开；落在段的开头或结尾时，摊到段的边界。
- SenseVoice 多出来的字：丢掉，只是不再借用它的时间。
- 再把带时间的字交给现有的 `transcript.Sentences` 按标点切句，后面的步骤都不用改。

对不上的风险：一段里两边差别太大（比如一边几乎什么都没认出来）时，摊出来的时间会偏很多。这时这一段**退回用 SenseVoice 的结果**，判断标准是对齐后对上的字不到 DeepSeek 文字的一半，上线前用数据校准这个比例。

### 失败了怎么办

- 每个请求遇到 408、429、5xx 和网络错误时等一会儿重试（1、2、4、8 秒，最多 5 次）。DeepSeek 的流式错误不存在（这个接口不流式），所以不会有大模型校对那样「200 里夹着错误」的问题。
- 某一段最后还是失败：这一段用 SenseVoice 的结果，其余段照用 DeepSeek 的；会议不失败。
- 401、403（Key 不对、欠费）：整场都用 SenseVoice，会议页面上提示「在线识别没用上：DeepSeek 的 API Key 不对」，并在设置页上显示最近一次的错误。
- 这场会议实际用了哪种识别方式记下来（每场会议存一个字段），会议页面「转写」标签旁边标出来，排查问题时也知道是哪个引擎的结果。

### 和现在的步骤怎么配合

- **区分说话人和在线识别同时做**：识别完 SenseVoice 后先把请求发出去，再在 CPU 锁里做区分说话人，两边都完了再对齐。一场 20 分钟的会议约 12 个请求，4 个并发约 15 秒，和区分说话人同时做，基本不增加处理时间（上线前在真实会议上量一下两边各要多久）。
- **按热词读音纠错、大模型校对照常做**，在 DeepSeek 的文字上做。DeepSeek 没有热词参数，专有名词要靠这两步（在 ContextASR 上它不带热词认对了 652/966 个，SenseVoice 加读音纠错是 802/966）。
- **重新转写**：按当时的设置重新走一遍，打开了在线识别就会重新发给 DeepSeek（重新计费）。
- **进度**：识别文字这一步的进度分两半：SenseVoice 占前一半，在线识别的请求完成数占后一半。不加新的阶段，网页不用改阶段名。

## 设置和界面

- 新的团队设置「语音识别」（存在 settings 表里，key 是 `asr`，不用改表结构）：
  - 识别方式：本地（默认）/ DeepSeek 在线识别
  - API Key：和大模型的 Key 一样加密存，网页上不回显
  - 接口地址：默认 `https://api.deepseek.com/v1/tools/asr`，一般不用改
- 接口：`GET/PUT /api/settings/asr`，`POST /api/settings/asr/test`（发 1 秒的静音，看 Key 能不能用）。只有管理员能改。
- 设置页上打开时写清楚：录音会发给 DeepSeek（深度求索）识别、按录音时长计费、可能受 DeepSeek 的数据政策约束；打开以后的会议才生效。

## 实测验证结果

在 191 上对四个数据集（共 1160 段、30.3 小时）实测的结果（完整表格见 [asr-eval.md](asr-eval.md#deepseek-在线识别loudnorm)）：

1. **线上方案的字错误率与退回率**：`deepseek-asr(线上)` 在 AliMeeting Eval / Test、AISHELL-4 Test、ContextASR 上的字错误率分别为 **25.78% / 25.11% / 15.71% / 3.08%**，和「合到 100 秒不拆句」完全一致；1160 段里 **1159 段对齐成功**，只有 1 段散会后闲聊退回 SenseVoice。测试中发现远场小声发言常被 SenseVoice 整句漏掉（DeepSeek 认出的字数比 SenseVoice 多 2～3 倍），单纯卡 `对上的字 / DeepSeek 总字数 >= 0.5` 会把救回来的小声发言误退回本机；补充「本机至少 8 字、长度差距不超过 5 倍且本机 60% 以上按顺序对得上也放行」后消除误退回。
2. **时间轴与说话人归属（cpCER）**：AliMeeting Eval / Test、AISHELL-4 Test 的带说话人错字率（cpCER）从 SenseVoice 的 39.23% / 39.89% / 25.93% 降到 **31.81% / 31.47% / 20.31%**（比 SenseVoice 低 5.6～8.4 个点；对照不拆句直接分配说话人时为 77.92% / 79.67% / 51.01%），验证了借用 SenseVoice 字级时间对齐分句的时间精度足够支撑说话人区分。
3. **专有名词纠错**：ContextASR 上 `deepseek-asr(线上)+拼音` 的字错误率已降到 **2.15%**（热词认对 **896/966**），单靠读音替换就已经优于 `sensevoice+拼音+大模型`（2.67%）；线上仍会继续接大模型校对。

## 已定决策

1. **开关粒度**：团队级设置（`local` 默认 / `deepseek` 可选），暂不加单场会议开关；涉密团队保持默认的本机识别即可。
2. **失败兜底**：单段请求重试后仍失败或时间轴对齐不上（`enoughMatch` 不满足）时，仅该段退回本机 SenseVoice；401/402/403 或全部段未用上时整场退回本机识别，在会议上记录 `asr_warning`、在设置状态里记录 `last_error`，不让会议失败。
3. **接口抽象**：`internal/cloudasr.Provider` 只保留 `Recognize(ctx, samples) (string, error)` 薄接口，目前仅接 DeepSeek。
